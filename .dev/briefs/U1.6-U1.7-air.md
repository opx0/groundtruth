# U1.6 and U1.7 — the two air sources

EPA AQS (historical monitor summaries) and AirNow (current preliminary
conditions) are the last two of the six sources in `docs/BRIEF.md` B2 without
an adapter. Both need a free key the operator has not registered yet, so
neither can be driven end to end from here. That blocks *running* them. It does
not block building them, and `lib/adapters/fema.ts` is the precedent: its NFHL
half is built against published field names, every record it produces carries a
caveat saying the shape is unverified against real bytes, and the gap is
visible in the report rather than hidden.

Do the same here, and be precise about which parts are verified.

## What is actually known, with evidence

**AQS response envelope — verified from EPA's own published documentation**,
reachable from this machine at
`https://aqs.epa.gov/aqsweb/documents/data_api.html`:

```json
{
  "Header": [ { "status": "success", "request_time": "2018-06-13T07:45:01-04:00", "url": "https://...", "rows": 1 } ],
  "Body": [ { "state_code": "01", "county_code": "073", "site_number": "0023", "parameter_code": "88101", "poc": 1.0, "latitude": 33.0, "longitude": -86.0, "datum": "WGS84", "parameter_name": "PM2.5 - Local Conditions", "...": "..." } ]
}
```

It is `Body`, not `Data`. `Header` and `Body` are both arrays. Read that page
yourself for the exact column list of each service you call — it differs per
service and the page lists them.

**AQS rate limit — verified live on 2026-09-16, real bytes committed** at
`tests/fixtures/aqs/rate-limited.json`:

```
HTTP/1.1 429 Too Many Requests
Retry-After: 86400
X-Powered-By: Air Quality Systems API, version 2
Content-Type: application/json

{"error":"Daily limit for account use exceeded. Retry later."}
```

EPA's published shared test account (`email=test@aqs.api&key=test`) is
exhausted and answers this to every request, including
`list/classes`. `lib/io/fetch-source-io.ts` already turns a 429 into
`SourceFailure("rate-limited", 429, "86400")` before parsing, so this is the
rate-limit case of the seven, from real bytes.

**AirNow unauthenticated — verified live on 2026-09-16, real bytes committed**
at `tests/fixtures/airnow/unauthenticated.json`:

```
HTTP/2 401
content-type: application/json;charset=UTF-8
www-authenticate: proprietary

{"WebServiceError":[{"Message":"Request not authenticated."}]}
```

So AirNow's error envelope is `WebServiceError`, an array of `{Message}`. That
much is now recorded fact. Its *success* shape is not: `docs/BRIEF.md` B2 marks
it unverified and it still is.

**From B2 and B14, verified earlier:** AQS is 10 requests per minute with a
5-second pause requested; begin and end dates must fall in one year except for
`monitors`; data can lag six months or more; parameters are `88101` PM2.5 and
`44201` ozone; services are `monitors/byBox`, `annualData/byBox`,
`dailyData/byBox`. AirNow observations update hourly and its rate limits are
documented behind a login. B2's boundary table: AQS 50 km, nearest qualified
PM2.5 monitor and nearest qualified ozone monitor, no result when none
qualifies; AirNow uses the reporting area it returns.

## Keys

Both keys come from `process.env` at the point of use and nowhere else. No key
is read at module load, no key appears in a committed file, no key reaches any
value the adapter returns, and no key appears in a payload URL that ends up in
provenance. `lib/adapters/census.ts` already solves the "the request URL
carries something the trace must not" problem — read its `citablePayload` and
do the same thing, for the same reason. A payload URL that carries a live API
key would put that key in the trace panel, on screen, for every reader.

An absent key is not a crash and not an empty result. It is a source that could
not be asked, and it must be distinguishable from one that answered with
nothing. Decide how to express that with the vocabulary the kernel already has
(`FailureCause` is a closed enum — read it), implement the honest option, and
say in your report if you think the enum is missing a member. Do not add one.

## Record kinds

Both kinds are already declared in `lib/evidence/records.ts` and you may not
change them:

- `aqs-monitor-summary`: `monitorId`, `pollutant`, `period`, `statistic`,
  `value`, `unit`, `observationCount`.
- `airnow-observation`: `reportingArea`, `pollutant`, `observedAt`, `aqi`,
  `category`, `concentration`, `unit`.

`pollutant` is typed `Sourced<"PM2.5" | "Ozone">` and no field reader produces
a literal union. It is not a value either agency sends in that vocabulary — it
is the parameter *we asked for*. `fromQuery` is the kernel's constructor for
exactly that: a value whose provenance is the request we made, the same way
`lib/adapters/fema.ts` sources its `dataset` field. Use it.

## Templates

`docs/BRIEF.md` A2 shows the air card as its template, because the values come
from the monitor:

> Nearest PM2.5 monitor: {monitor}, {distance} km from the mapped point.
> {year} annual mean: {value} {unit}. The monitor measures its own location,
> not this address. AQS data lags collection by 6 months or more.

Read `.dev/briefs/U2.0-record-templates.md` in full — every rule in it applies
to you — and `lib/templates/sems.ts` for the register. Note that the last two
sentences of the A2 copy are caveats: decide which belong in a clause carrying
a reference (so they cannot outlive the value they qualify) and which belong in
the record's `caveats`, and say why.

## Fixtures you author rather than record

You will have to write payloads for the success cases, because no real ones
exist. Three rules:

1. A fixture you wrote is not a recording and must never be filed as one. Name
   every such file with a `derived-` prefix, and put a sibling `.source.md`
   next to it naming the exact documentation URL and the date, and stating that
   the bytes were constructed from a published field list rather than captured.
2. Its field names and types come from the published documentation, not from
   your expectations. Where the documentation does not say, do not invent:
   leave the field out of the schema and out of the record.
3. Every record built from a derived shape carries a caveat saying so, in the
   same words `lib/adapters/fema.ts` uses for NFHL. The reader must be able to
   see, on the card, that this shape has never been checked against a real
   response.

## Acceptance

1. `pnpm exec tsc --noEmit` clean; `pnpm exec eslint <your files>` clean; a
   targeted `pnpm exec vitest run <your test files>` green. Real output pasted.
2. The seven `docs/BRIEF.md` B12 cases for your source: success, no records,
   missing optional fields, unknown status, malformed response, rate limit,
   timeout. The rate limit (AQS) and the unauthenticated case (AirNow) use the
   committed real bytes. Assertions are literal normalized records, including
   units, timestamps, IDs and provenance.
3. A test proves no API key appears in any returned value, any payload URL, any
   provenance, or any thrown error, with the key set to a recognisable
   sentinel.
4. A test proves an absent key produces an unavailable outcome that is
   distinguishable from a source that answered with no records.
5. A test renders each template against a built record and asserts the exact
   whole sentence.
6. Zero type assertions, non-null assertions or `any`.
7. Unknown statuses and unit strings survive verbatim; no `z.enum()` over an
   agency's vocabulary.
