# U3.1 — the report route

The hard tier. Every source runs for one confirmed coordinate and every source
streams its own result, so one slow source cannot hold the page. ECHO's
five-mile query at the demo point answers 1,686 facilities from a host that
needs a 45-second timeout; SEMS answers in about a second. A report that waits
for both shows nothing for 45 seconds, and `docs/BRIEF.md` A6 beat 2 is "cards
resolve independently".

`lib/io/fetch-source-io.ts` is the real network layer. It has been exercised by
exactly one route so far.

## The request carries coordinates and nothing else

`docs/BRIEF.md` B9 step 5: the browser sends the confirmed coordinate and match
metadata to the report route. Step 6: environmental adapters receive
coordinates and query parameters only.

So the request body is a latitude and a longitude. Not an address, not a
matched address, not a tiger line. Validate it with zod, reject anything else
with the same shape of response the geocode route uses for an invalid body.

The radius is **not** in the request. It is a product decision per source, out
of B2's boundary table: five miles for ECHO, SEMS and FRS; fifty kilometres for
AQS; the exact point for FEMA. `Locus` carries one radius, so build a locus per
source rather than passing one around. Name the constants and say where each
number comes from.

## The origin sentences do not come from this route

A `GeocodeMatch` holds `Sourced` values, and there is no exported way to build
one — the kernel forbids it, deliberately. So the report route cannot
reconstruct the match from the coordinates the browser sends, and it must not
try. The match exists in exactly one place: `app/api/geocode/handler.ts`, which
holds it already.

That is the right answer rather than a limitation. It means the report route
never touches a value derived from the address.

**So this unit also changes the geocode route** to return the rendered origin
sentences beside the match view it already returns, and deletes
`buildPrecisionSentence` from `app/lib/geocode-contract.ts`. That function
writes `docs/BRIEF.md` A2's precision sentence as a hand-written template
string, in a codebase whose entire claim is that code renders every sentence
from the agency's own fields. `lib/templates/origin.ts` has rendered that
sentence since it was written and nothing has ever called it. Wire it up, and
update `app/components/confirm-screen.tsx` and `tests/unit/app/screens.test.ts`
to consume the rendered sentence instead.

## What crosses the wire

A rendered sentence is spans, and the trace panel (U4.3) needs what stands
behind each span. Two constraints shape this:

1. **One trace per sentence, not per span.** `trace(store, sentence, i)`
   returns `{scope, <the scope's header>, clicked, values}`, and only `clicked`
   differs between the spans of one sentence — `values` and the header are
   identical. Shipping a trace per span ships the same payload five times.
   Ship it once and let the browser find the clicked value in `values` by the
   span's field name.
2. **Do not ship `Sentence.subject`.** For an origin sentence the subject is
   the whole `GeocodeMatch`, provenance and payload included, and the geocode
   handler goes to some trouble not to send that. `verify()` is a server-side
   property with tests on it; it is not something the browser does.

Define the wire types in `app/lib/report-contract.ts` with zod schemas, and
parse every message through them before it goes out, the way `respond()` does
in the geocode handler. A zod object schema strips keys it was not told about,
which is the backstop that catches a field someone attaches by mistake later.

## Streaming

Newline-delimited JSON, one event per line, `Content-Type: application/x-ndjson`,
a `ReadableStream` the route returns immediately. Each event is a discriminated
union member with its own zod schema.

At minimum: one event per source card as that source settles, one event for the
facility groups once every source has settled (grouping needs records from more
than one source, so it cannot be per-card), and a terminal event.

Rules:

- **A failing source is a card, not a stream error.** `runSource` never
  rejects; it returns an unavailable outcome. The stream ends only when every
  source has settled or the client disconnects.
- **The order of the events is the order the sources settle**, not a fixed
  order. The card carries its own identity; the browser places it.
- If the whole thing fails before any card, say so in one event and end. Do not
  leave a stream open.

Decide how a card's chrome numbers are computed — B7's "up to five records" and
"View all when a section holds more" need a total and a carried count — and
read `lib/report/selection.ts`'s module comment on why the plan does not carry
them. They are computed from the store at render time, next to the count
sentence they must agree with. A card that carries fewer records than the
section holds must say so; a bound the reader cannot see is a lie.

## The flood card calls the flood adapter directly

`.dev/PLAN.md` queue item 8. `runSources`' shared fan-out gives the flood slot
one `SourceOutcome` with no way to say which of the two datasets answered, and
that distinction is the entire reason the card exists — B10 gives the two
datasets deliberately different no-polygon wordings and B12 requires a
no-polygon state to name its dataset.

`floodZoneOutcome(locus, io, policy)` returns the dataset beside the outcome
and the NFHL failure that forced the fallback. Use it. Note that
`FloodZoneResult.nfhl` being non-null means the authoritative layer failed and
Esri answered instead; the selection policy decides how that surfaces.

## FRS runs after SEMS

`lookupFrsFacility` takes a registry ID, not a locus: FRS is an identity lookup
and a five-mile radius query answers 6,915 interest rows. So the FRS card
depends on which records the report is showing, and it cannot start until SEMS
has settled. That is a real dependency, not an accident — state it in the
module comment, keep the number of lookups bounded, and name the bound.

Every other source starts at once.

## AQS and AirNow

Neither has an adapter; both are blocked on a key the operator must register
(`.dev/briefs/U1.6-U1.7-air.md`). B7 still says the summary shows the status of
every source.

Build the source table so that adding those two is a registration and not a
redesign, and decide what the report says about them meanwhile. Whatever you
choose must be honest: a source nobody asked is not a source that answered with
nothing, and it is not a source that refused. Say what you chose and why. Do
not add a member to `FailureCause` — if you believe the enum is missing one,
put that in your report.

## Privacy

`docs/BRIEF.md` B9's last paragraph. Hold all of it, and note which parts this
route makes easier than the geocode route did:

- No address reaches this route at all, by the shape of the request. Say so in
  the module comment; it is the strongest privacy property in the codebase and
  it should be visible to the next reader.
- **No coordinate in any log line or error payload.** The geocode handler's
  rule — a fixed string and an enum value, never an error's own `.message`,
  never anything derived from the request — holds here too, and here the thing
  that must not leak is the coordinate.
- **No cache key tied to a user, session, IP or browser.** There is no cache in
  this unit (U3.2 adds one); do not add one.
- **A payload URL must never carry a key.** AQS and AirNow take their keys as
  query parameters, and a payload URL ends up in the trace panel, on screen.
  Those adapters do not exist yet and their brief makes redaction their job,
  but a second check here costs nothing and catches the case where they get it
  wrong. Add it, and test it with a recognisable sentinel.

## Acceptance

Every item is a command or an assertion.

1. `pnpm verify` green and `bash .dev/census/mutation-check.sh` 8 of 8. Paste
   the real output of both.
2. A test drives the whole route from a fixture-backed `SourceIo` and asserts
   the exact sequence of events for the Houston demo point, including the
   rendered text of at least one sentence per card.
3. A test proves a source that fails produces a card saying so, and that every
   other card still arrives. Make one source throw, one time out, and one
   answer with no records, in the same run.
4. A test proves the events arrive as the sources settle rather than in a fixed
   order: make a slow source and a fast one, and assert the fast card is
   emitted first.
5. A test proves the flood card names its dataset, in both the polygon and the
   no-polygon case, and that the no-polygon wording differs between NFHL and
   Esri.
6. A test proves no request the adapters receive carries an address, and that
   no log line and no response body contains the coordinate. Assert against a
   captured console, not by reading the code.
7. A test proves a payload URL carrying an API key does not reach the wire.
8. A test proves the trace that crosses the wire is enough to answer "what
   field is behind this span" for every span of every sentence in a card.
9. A test proves the geocode route's origin sentences are rendered by
   `lib/templates/origin.ts` and that `buildPrecisionSentence` is gone.
10. Zero type assertions, non-null assertions or `any` anywhere you touched.

## Forbidden

No new dependencies. No network in tests. No git commands — leave the tree
dirty. Do not add a cache. Do not edit `lib/evidence/**`,
`lib/report/selection.ts`, `lib/templates/**`, `lib/adapters/**`, or
`tests/fixtures/**`. If you need a change in any of those, do not make it; put
it in your report with the reason.

## Report, 25 lines maximum

Files written. Real `pnpm verify` and mutation-check output. The event schema,

chrome numbers are computed and where. The FRS bound and why that number. One
