# U4.2 and U4.3 — the report screen and the trace panel

Screen 3 and screen 4 of `docs/BRIEF.md` A2. Everything behind them is built:
the report route streams a card per source as it settles, each card carries
rendered sentences, and each sentence carries the trace that explains every one
of its spans. Nothing in this unit decides what a sentence says, what order
records appear in, or which template a record gets. If you find yourself
wanting to, the answer is in `lib/report/selection.ts` and you may not edit it.

What this unit decides is what a reader sees, in what order, and what happens
when they click.

## Reading order

1. `docs/BRIEF.md` A2 (all four screens), A3 (the trace panel, row by row — it
   is a table and every row of it is a requirement), A5 (what the report tells
   you it cannot do, and where those limits go), A6 (the demonstration, beat by
   beat — this is what the screen is judged on), B10 (failure behaviour).
2. `app/lib/report-contract.ts` — the wire types and their zod schemas. This is
   the whole of what you have to work with. Read `SentenceViewMessage`,
   `CardView`, `ListingView` and the trace arms.
3. `lib/report/sentence-view.ts` — its module comment says why there is one
   trace per sentence and how to find the clicked value from a span.
4. `app/components/search-flow.tsx`, `confirm-screen.tsx` — the component shape
   this codebase already uses, including how the confirm screen renders origin
   sentences with `data-field` on each slotted span. You are extending that
   pattern, not inventing one.
5. `app/lib/geocode-flow.ts` — the reducer pattern, and why its state shape is
   where the privacy rule lives rather than in prose.

## What you build

Named in your task. The two halves are:

**The report screen.** A component that takes the confirmed match, calls the
report route, consumes the NDJSON stream, and renders cards as they arrive.
Plus the state machine behind it, in its own file, testable without rendering.

**The trace panel.** Clicking any slotted span opens what stands behind it:
`docs/BRIEF.md` A3's table is the specification and every row of it has a
source in `SentenceViewMessage`'s trace. Build A3's table, row for row, and for
each row say in your report where the value came from — or that the wire does
not carry it, which is a finding rather than a gap to paper over.

## The rules that are not yours to bend

**No component writes a factual sentence.** Not a count, not a status, not a
distance, not a date. Every one of those is a span the server rendered, and the
screen's job is to put spans on screen with their `data-field` intact. Interface
chrome — a heading, a button, "Showing 5 of 15", "Retry", a loading state — is
the screen talking about itself and is fine. The test of whether a string is
chrome: could it be wrong because a government record changed? Then it is not
chrome and you may not write it.

**A card that has not arrived is not a card that is empty.** The stream sends
cards as sources settle, and B10's three states are already distinct on the
wire. A fourth state — still waiting — belongs to the screen, and it must look
like none of the other three.

**`docs/BRIEF.md` C2's words never appear.** Not in a heading, not in a tooltip,
not in an aria-label, not in a colour that means a verdict. There is no severity
palette: a card for a Superfund site and a card for a flood zone get the same
treatment, because ranking them is the score this product refuses to compute.

**Every limit goes on the card it limits** (A5), not in a footer. The limits are
already sentences on the wire — the caveats in a record's trace, the not-shown
sentence, the no-polygon note that names its dataset. Put them where the reader
reads the claim, not where the layout is tidiest.

## Things the wire will make you confront

These are real and known, from the audits that ran over the route. Handle them
deliberately and say what you did:

- **A source that was never asked.** AQS and AirNow have adapters but are not
  registered, so their cards arrive with `state: "not-asked"` and no status
  sentence. That is neither "answered with nothing" nor "could not be reached",
  and the screen has to make the difference visible without writing a claim.
- **The gap before the end.** `groups` and `end` wait for the slowest source,
  and ECHO's budget is 45 seconds. Five cards land in about 120 ms and then the
  stream is open and silent. Nothing on the wire says which sources are
  outstanding — decide what the screen shows in that window, and if you think
  the wire should say more, put it in your report rather than guessing.
- **27 of 172 spans resolve to a value with an empty `provenance` array.** Every
  status sentence and every count sentence is one: their grounding is on the
  scope header (`SourceTrace`, `SectionTrace` with its `counted` list) rather
  than on the value. A trace panel that renders only `values[].provenance` shows
  an empty citation on every one of them. Render the header.
- **`SectionTrace.query` is null on every section.** Clicking "5 miles" has the
  boundary string and nothing else behind it. Show what is there and do not
  invent what is not.
- **A record trace carries `caveats`**, and for AQS and AirNow those include
  that the response shape has never been checked against a real response. A5
  says limits go on the card.

## Acceptance

1. `pnpm verify` green and `bash .dev/census/mutation-check.sh` 8 of 8. Paste
   real output of both.
2. Tests drive the real components against a real NDJSON stream built from the
   committed fixtures through the real route handler — not against invented
   card objects.
3. A test proves cards render in arrival order and that a slow source does not
   delay a fast card's appearance.
4. A test proves the four card states look different from each other: answered
   with records, answered with nothing, could not be reached, never asked.
5. A test proves clicking any slotted span of any sentence in any card opens a
   panel naming the agency, the record, the raw field and the raw value behind
   that span — walked across every span, not sampled.
6. A test proves no rendered string outside a span was written by a component:
   collect every text node the screen produces, subtract the spans the server
   sent, and assert what is left is chrome you can enumerate.
7. A test greps the rendered output for every word in `docs/BRIEF.md` C2.
8. Zero type assertions, non-null assertions or `any`.

## Forbidden

No new dependencies — no component library, no state library, no markdown
renderer. Tailwind is already here and is the styling. No network in tests. No
git commands. Do not edit `lib/**`, `app/api/**`, `app/lib/report-contract.ts`,
`docs/**` or `tests/fixtures/**`. If you need a change in any of those, do not
make it; put it in your report with the reason.

## Report, 25 lines maximum

Files. Real command output. A3's table, row by row, with where each row's value
comes from or the note that the wire does not carry it. What the screen shows
for each of the four card states and during the wait. Every string a component
writes, enumerated — that list is the thing a reviewer checks hardest. One line
per acceptance item naming the test. Anything you had to work around.
